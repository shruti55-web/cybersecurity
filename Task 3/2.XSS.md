# Cross-Site Scripting (XSS) — DVWA

Cross-Site Scripting (XSS) is the second vulnerability covered in this Web Application Security Internship. This practical exercise focuses on understanding and testing Stored XSS and Reflected XSS using Damn Vulnerable Web Application (DVWA).

Both vulnerabilities were tested in a controlled DVWA environment at Low security. The exercise also covers security mechanisms such as Input Validation, Output Encoding, and Content Security Policy (CSP).

---

## What is Cross-Site Scripting (XSS)?

Cross-Site Scripting (XSS) is a web application vulnerability that occurs when an application accepts untrusted user input and includes it in a webpage without properly validating or encoding it.

As a result, the browser may interpret the supplied content as executable HTML or JavaScript instead of displaying it as ordinary text.

In simple terms, an attacker may insert malicious JavaScript into a vulnerable website, causing the script to execute in another user's browser when the affected page is viewed.

The fundamental problem is similar to SQL Injection:

**Untrusted input is treated as code instead of data.**

In SQL Injection, the injected content affects database queries. In XSS, it affects HTML and JavaScript interpreted by the browser.

### Types of XSS

There are three major types of Cross-Site Scripting:

| Type | Where the payload lives | Who gets affected |
|---|---|---|
| Stored XSS | Stored in the application's database or server-side storage | Users who view the affected content |
| Reflected XSS | Reflected immediately in the server's response | Users who open the crafted request |
| DOM-based XSS | Processed unsafely by client-side JavaScript | Users who interact with the affected page |

This practical exercise focuses on Stored XSS and Reflected XSS.

# 1. Stored Cross-Site Scripting (Stored XSS)

## What is Stored XSS?

Stored XSS, also known as Persistent XSS, occurs when an application stores untrusted input and later displays that content to users without properly encoding or sanitizing it.

Since the malicious content is stored on the server, it may affect multiple users who visit the affected page.

## Where it was tested

**DVWA → XSS (Stored)**

DVWA provides a guestbook-style form containing fields such as:

- Name
- Message

When a user submits information, the application stores the submitted content in its database and displays it on the webpage.

## Test Payload

The following harmless JavaScript payload was used to test the vulnerability:

```html
<script>alert('Stored XSS')</script>
```

The payload was entered into the Message field and submitted.

## What happens behind the scenes?

1. The user enters the JavaScript payload in the Message field.
2. The application receives the submitted input.
3. The application stores the content in its database.
4. When the guestbook page loads, the stored content is retrieved.
5. If the application displays the content without proper output encoding, the browser interprets the script.
6. A JavaScript alert box appears.

The alert box demonstrates that JavaScript supplied through user input is being executed by the browser.

## Why is Stored XSS dangerous?

Stored XSS is particularly dangerous because the malicious content remains saved in the application.

Unlike Reflected XSS, the attacker does not necessarily need to send a separate crafted link to every affected user. Anyone who visits the affected page may trigger the stored script.

### Possible Impact

- Unauthorized actions performed through a victim's browser.
- Exposure of information accessible to page scripts.
- Session-related security risks.
- Modification of webpage content.
- Phishing attacks through fake login interfaces.
- Damage to application reputation and user trust.

For example, if session cookies are accessible to JavaScript, an XSS vulnerability could expose them. Using HttpOnly cookies helps prevent direct JavaScript access to those cookies, although it does not eliminate every consequence of XSS.

# 2. Reflected Cross-Site Scripting (Reflected XSS)

## What is Reflected XSS?

Reflected XSS, also known as Non-Persistent XSS, occurs when an application takes user input from an HTTP request and immediately includes it in the response without proper output encoding.

Unlike Stored XSS, the malicious input is generally not saved in the database.

Instead, it is reflected directly in the webpage.

## Where it was tested

**DVWA → XSS (Reflected)**

The DVWA Reflected XSS page accepts a value through a URL query parameter named `name`.

The application displays a greeting using the supplied value.

For example:

```text
http://localhost/DVWA/vulnerabilities/xss_r/?name=Shruti
```

## Test Payload

The following harmless JavaScript payload was used:

```html
<script>alert('Reflected XSS')</script>
```

It was supplied through the URL query parameter.

## What happens behind the scenes?

1. A user submits a request containing a value in the `name` parameter.
2. The server receives the request.
3. The application reads the supplied parameter.
4. The value is inserted into the webpage without appropriate output encoding.
5. The browser interprets the injected script.
6. A JavaScript alert box appears.

The input is not stored permanently. It is reflected in the immediate response.

## How is it delivered?

A Reflected XSS vulnerability may be exploited by convincing a victim to open a specially crafted link.

For example, an attacker may send a malicious URL through email or messaging platforms.

When the victim opens the link, the vulnerable application may reflect the supplied input into the response.

This is why Reflected XSS is commonly associated with phishing and social engineering.

### Possible Impact

- Unauthorized actions in the victim's browser.
- Manipulation of webpage content.
- Phishing and fake login interfaces.
- Exposure of information accessible to page scripts.

---

# 3. Difference Between Stored XSS and Reflected XSS

| Stored XSS | Reflected XSS |
|---|---|
| Also called Persistent XSS | Also called Non-Persistent XSS |
| Malicious input is stored by the application | Malicious input is reflected in the immediate response |
| Can affect users who visit the affected page | Usually requires the victim to open a crafted request |
| Common in comments, guestbooks and profile fields | Common in search pages and URL parameters |
| May execute repeatedly until the stored content is removed or corrected | Usually executes when the crafted request is processed |

# 4. XSS Mitigation Techniques

Preventing XSS requires proper handling of user input and safe rendering of application output.

## A. Input Validation

Input Validation means checking user-supplied data before accepting or processing it.

For example, if a form expects a person's name, the application should validate that the supplied value follows the expected format.

Validation can include:

- Checking permitted characters.
- Checking maximum input length.
- Rejecting unexpected data types.
- Enforcing application-specific input rules.

However, simply blocking characters such as `<`, `>`, or `script` is not sufficient.

Attackers may use alternative HTML elements, encoding techniques, and event handlers to bypass weak filters.

Therefore, Input Validation should be combined with context-aware Output Encoding.

## B. Output Encoding — The Primary Defense

Output Encoding ensures that untrusted user input is displayed as ordinary text instead of being interpreted as executable HTML or JavaScript.

### Vulnerable PHP Code

```php
echo 'Hello, ' . $_GET['name'];
```

The application directly inserts user input into the HTML response.

This can result in XSS if the input contains executable markup.

### Secure PHP Code

```php
echo 'Hello, ' .
htmlspecialchars(
    $_GET['name'],
    ENT_QUOTES,
    'UTF-8'
);
```

The `htmlspecialchars()` function converts special HTML characters into their corresponding HTML entities.

### Character Encoding Table

| Character | Encoded representation |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#039;` |
| `&` | `&amp;` |

For example:

```html
<script>alert(1)</script>
```

When properly HTML-encoded, the browser displays the content as text rather than interpreting it as a script element.

**Important:** `htmlspecialchars()` is appropriate for HTML text and quoted HTML attribute contexts when used correctly. JavaScript, CSS, and URL contexts require their own safe handling.

## C. Content Security Policy (CSP)

Content Security Policy is an additional browser security mechanism that restricts which resources a webpage is allowed to load or execute.

It is generally configured through an HTTP response header.

### Example CSP Header

```apache
Header set Content-Security-Policy "default-src 'self'; script-src 'self'"
```

### Explanation

- `default-src 'self'`: Allows resources from the application's own origin by default.
- `script-src 'self'`: Restricts script loading to the application's own origin and blocks inline scripts unless separately authorized.

A properly configured CSP can reduce the impact of certain XSS vulnerabilities by restricting script execution.

However, CSP is an additional security layer and does not replace proper input handling and output encoding.

### Enabling Apache Headers Module

Execute the following commands in Kali Linux:

```bash
sudo a2enmod headers
```

Restart Apache:

```bash
sudo systemctl restart apache2
```

The CSP header must also be configured in the appropriate Apache virtual host or application configuration.

# 5. Verifying the Mitigation

After applying security controls, the application should be tested again to confirm that the vulnerability has been addressed.

### Testing at Different DVWA Security Levels

| Security Level | General behavior |
|---|---|
| Low | Minimal protection; vulnerable behavior can be demonstrated |
| Medium | Introduces basic filtering that may be bypassable |
| High | Applies stronger input handling, but protection depends on the implementation |

### Expected Observations

- At Low security, the harmless test payload may execute.
- At Medium security, basic filters may block some payloads but are not necessarily sufficient.
- After implementing correct output encoding, the payload should appear as ordinary text rather than execute in the relevant HTML context.
- With a properly configured CSP, unauthorized script execution may also be blocked.

**Note:** DVWA's security levels are intentionally designed for training. They should not be treated as a substitute for secure production application development.

# 7. Conclusion

Cross-Site Scripting is a serious web application vulnerability that allows untrusted input to be interpreted as executable content in a user's browser.

Through the DVWA exercises, Stored XSS and Reflected XSS demonstrate two different ways in which unsafe input handling can lead to JavaScript execution.

The practical study also highlights the importance of Input Validation, context-aware Output Encoding, and Content Security Policy.

Output Encoding is the primary defense against XSS, while CSP provides an additional layer of browser-side protection.

Understanding these vulnerabilities helps developers build safer web applications and helps security testers identify weaknesses before they can be exploited.
