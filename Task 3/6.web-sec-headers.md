# Web Security Headers — SecurityHeaders.com and Apache Configuration

## 1. Introduction to Web Security Headers

HTTP security headers are instructions sent by a web server to a browser through HTTP responses.

These headers tell the browser how to handle website content and which security restrictions should be applied.

They help protect web applications against common security risks such as:

- Cross-Site Scripting (XSS)
- Clickjacking
- MIME-type sniffing
- Information leakage
- Insecure communication

Security headers are an additional layer of protection. They do not replace secure coding, authentication, input validation, or other security practices.

## 2. What Are HTTP Request and Response Headers?

HTTP communication generally involves a client and a server.

- **Request Headers:** Information sent by the browser to the web server.
- **Response Headers:** Information sent by the web server back to the browser.

For example, when a user opens a website, the browser sends an HTTP request. The server processes it and returns an HTTP response containing website content and response headers.

Security headers are generally configured in the server's HTTP responses.

## 3. Important HTTP Security Headers

### 1. Content-Security-Policy (CSP)

CSP stands for Content Security Policy.

It helps control which sources a browser is allowed to load scripts, stylesheets, images, and other resources from.

It can reduce the impact of certain Cross-Site Scripting (XSS) attacks.

Example:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

**Explanation:**

- `default-src 'self'`: Uses the same origin as the default permitted source.
- `script-src 'self'`: Allows scripts from the same origin.
- Inline scripts and scripts from unapproved external sources are restricted by this policy.

The exact policy should be designed around the website's actual requirements. A restrictive CSP can break website functionality if legitimate external resources or inline scripts are required.

### 2. X-Frame-Options

This header helps protect websites against clickjacking.

Clickjacking is an attack in which a user is tricked into interacting with a website through an embedded or hidden frame.

Example:

```http
X-Frame-Options: DENY
```

**Explanation:**

- `DENY`: Prevents the page from being displayed inside frames.
- `SAMEORIGIN`: Allows framing only by pages from the same origin.

For modern browsers, CSP's `frame-ancestors` directive is the preferred flexible control.

### 3. X-Content-Type-Options

This header prevents browsers from trying to guess a resource's content type when MIME-type sniffing is disabled.

Example:

```http
X-Content-Type-Options: nosniff
```

**Explanation:**

The `nosniff` value tells the browser to respect the declared content type rather than attempting to interpret the resource as another type.

### 4. Strict-Transport-Security (HSTS)

HSTS stands for HTTP Strict Transport Security.

It instructs browsers to use HTTPS when communicating with a website after receiving the policy over a secure HTTPS connection.

Example:

```http
Strict-Transport-Security: max-age=31536000
```

**Explanation:**

- `max-age`: Specifies how long the browser should remember the HTTPS-only policy.
- `31536000`: Represents one year in seconds.

**Important:** Configure HSTS only when the website is correctly served over HTTPS. Do not add it to a simple HTTP-only localhost DVWA lab.

### 5. Referrer-Policy

This header controls how much information about the previous page is shared when the browser navigates to another resource.

Example:

```http
Referrer-Policy: strict-origin-when-cross-origin
```

**Explanation:**

It generally sends the full referrer URL for same-origin requests and only the origin for cross-origin requests, while omitting it when navigating from HTTPS to HTTP.

### 6. Permissions-Policy

This header controls whether selected browser features and APIs can be used by a website or embedded content.

Example:

```http
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

**Explanation:**

This example disables access to the camera, microphone, and geolocation features for the page and its embedded content.

Only disable features that the application does not need.

## 4. Practical 1 — Analyze a Website Using SecurityHeaders.com

### Objective

To analyze the HTTP security headers of an authorized test website and understand which security headers are present or missing.

### Tool Used

SecurityHeaders.com

Website:

https://securityheaders.com/

### What Is SecurityHeaders.com?

SecurityHeaders.com is an online tool that analyzes a website's HTTP response headers.

It checks the security-related headers returned by the website and provides a report showing its security-header configuration.

The report can help identify missing or incorrectly configured headers.

### Testing Steps

1. Open a browser.
2. Visit https://securityheaders.com/.
3. Enter the URL of a website that you own or are authorized to test.
4. Start the scan.
5. Wait for the analysis to complete.
6. Review the security grade and header results.
7. Identify which headers are present.
8. Identify which recommended headers are missing or incorrectly configured.
9. Save a screenshot of the report for your internship documentation.

### Understanding the Results

The tool may show:

- Overall security grade.
- Present security headers.
- Missing security headers.
- Header configuration details.
- Recommendations for improving the configuration.

**Important:** SecurityHeaders.com is an external service. It cannot directly access `http://localhost/DVWA/` on your Kali machine because localhost is not publicly reachable. Use an authorized publicly accessible test website for this scan. You can separately verify your local Apache configuration using browser developer tools or terminal commands.

## 5. Practical 2 — Configure HTTP Security Headers in Apache

### Objective

To configure appropriate HTTP security headers in the Apache web server and verify that the server includes them in its responses.

### Testing Environment

- Operating System: Kali Linux
- Web Server: Apache
- Application: DVWA (local lab)
- Configuration File: Apache security headers configuration
- Module: mod_headers

### What Is mod_headers?

`mod_headers` is an Apache module that allows administrators to modify HTTP request and response headers.

It can be used to add, replace, or remove HTTP headers.

### Step 1: Check Apache Status

Open the Kali Linux terminal and execute:

```bash
sudo systemctl status apache2
```

Confirm that Apache is running.

### Step 2: Enable the Headers Module

Execute:

```bash
sudo a2enmod headers
```

This enables Apache's `headers` module.

### Step 3: Create a Security Headers Configuration File

Create a new configuration file:

```bash
sudo nano /etc/apache2/conf-available/security-headers.conf
```

Add the following configuration:

```apache
<IfModule mod_headers.c>

    Header always set X-Content-Type-Options "nosniff"

    Header always set X-Frame-Options "SAMEORIGIN"

    Header always set Referrer-Policy "strict-origin-when-cross-origin"

    Header always set Content-Security-Policy "default-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self'"

    Header always set Permissions-Policy "camera=(), microphone=(), geolocation=()"

</IfModule>
```

Save the file and exit the editor.

**Configuration Explanation:**

- `X-Content-Type-Options`: Helps prevent MIME-type sniffing.
- `X-Frame-Options`: Restricts framing to the same origin.
- `Referrer-Policy`: Controls referrer information shared with other origins.
- `Content-Security-Policy`: Restricts resource loading and framing.
- `Permissions-Policy`: Disables selected browser features.

**Important:** This is an example baseline, not a universal policy. CSP may interfere with DVWA's functionality. Test the application after enabling it and adjust the policy to allow only the resources the application legitimately requires. Do not weaken the policy blindly just to remove browser errors.

HSTS is intentionally not included because the local lab is using HTTP. Add HSTS only after correctly configuring HTTPS.

### Step 4: Enable the Configuration

Execute:

```bash
sudo a2enconf security-headers
```

This enables the newly created Apache configuration.

### Step 5: Check Apache Configuration

Before restarting Apache, execute:

```bash
sudo apache2ctl configtest
```

Expected successful result:

```text
Syntax OK
```

If Apache reports an error, correct the configuration before continuing.

### Step 6: Restart Apache

Execute:

```bash
sudo systemctl restart apache2
```

Check the service again:

```bash
sudo systemctl status apache2
```

### Step 7: Verify the Headers

Use the following command:

```bash
curl -I http://localhost/DVWA/
```

The response should include the configured security headers, provided the request is handled by the Apache configuration where they were enabled.

Example of expected response-header lines:

```http
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
Referrer-Policy: strict-origin-when-cross-origin
Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self'
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

The actual response may contain additional headers.

### Step 8: Verify Using Browser Developer Tools

1. Open Firefox.
2. Visit `http://localhost/DVWA/`.
3. Press F12 to open Developer Tools.
4. Select the Network tab.
5. Reload the page.
6. Select the main document request.
7. Open the Response Headers section.
8. Check whether the configured headers are present.

Take a screenshot of the results.

## 8. Conclusion

HTTP security headers provide an additional layer of protection for web applications by controlling how browsers handle website content and resources.

In this practical exercise, SecurityHeaders.com was used to analyze an authorized test website's HTTP security headers. Apache's `mod_headers` module was then used to configure security headers in the local web server.

The configuration was verified using terminal commands and browser developer tools.

Properly configured security headers can help reduce risks such as clickjacking, MIME-type sniffing, information leakage, and certain XSS-related attacks.
